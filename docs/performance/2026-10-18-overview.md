# Performance overview — 18 October 2026

This pass compares the accepted `aca9768` integration with production change `a3f78fa`. It improves CPU evaluation without reducing rollout counts, removing candidates, changing random seeds, or approximating decision values. Independent Standards and Spec reviews accepted production change `a3f78fa`; the final benchmark additions are reviewed at `09174bb`.

The project is faster on the measured fixtures, but it has not reached a universal 100 ms response time. Large fresh Engine evaluations still exceed the Engine budget. Capture, OCR, the game-running Windows process, IPC and renderer presentation need separate measurements before an end-to-end latency claim is possible.

## Measurements

The companion `2026-10-18-results.json` records the unprofiled samples, fixture settings and parity results. Medians describe this macOS ARM64 machine with Python 3.14.7. They are synthetic software measurements, not recognition accuracy, fitted-model quality, gameplay results or Ryzen 7 7800X3D qualification. Profiled timings were used to locate costs and are excluded from speedup calculations.

| Workload | Baseline | Optimized | Speedup |
| --- | ---: | ---: | ---: |
| Fresh planning: 65 Guides, 64 rollouts | 316.5 ms | 266.7 ms | 1.19× |
| Fresh combat fixture: 65 Guides, 64 rollouts | 330.5 ms | 282.1 ms | 1.17× |
| Fresh two-slot roster: 65 Guides, 64 rollouts | 912.5 ms | 572.3 ms | 1.59× |
| Fresh augment choice: 12-option pool, 8 Guides, 8 rollouts | 1,832.4 ms | 1,659.6 ms | 1.10× |
| Repeated Live input: 65 Guides, 64 rollouts | 344.7 ms | 59.6 ms | 5.79× |
| Repeated Live input: 12 historical snapshots, small fixture | 75.5 ms | 17.3 ms | 4.36× |
| First replay production: 300 decisions, small fixture | 7,825.0 ms | 7,258.4 ms | 1.08× |

Engine and Live values are medians of the recorded repetitions. The Live series includes its first evaluation; the optimized 65-Guide first evaluation took 308.5 ms before the memo was warm. Repeated-input speedups do not describe changed gold, ownership, offers or other stochastic inputs. The replay row has one fresh process per checkout and is directional, not a repeated-sample estimate.

For that 300-decision replay, peak process RSS was 146.6 → 144.8 MiB; retained RSS was 132.7 → 129.9 MiB. Both serialized outputs contained 8,246,986 bytes. Both checkouts reported clean relevant sources and no loaded-runtime mismatches. This fixture does not qualify long-game resources.

## What changed

- **Historical planning:** Live now retains the existing causal planning fold. Equivalent snapshots reconstructed from storage can reuse an earlier plan. A changed snapshot, sighting, data object or hook registry invalidates the affected prefix. The current decision still runs through planning and freshness checks.
- **Repeated simulation inputs:** Live retains an LRU memo with at most 32 simulation entries and 32,768 rollout/projection accounting units. Its keys include the immutable data identity, semantic fields, resolved effects, opponents, concrete Lines, seed and Backup. Entries retain their data object until eviction, preventing recycled object identities from matching old results. New games, changed data and direct non-Live calls reset the advisor's cache. Evicted states are recomputed in full.
- **Patch preparation:** Power, capacity rules, slot costs, par counts and model fingerprints reuse immutable calculations during one synchronous evaluation. Nested choice evaluations share the request scope while retaining separate data identities. The scope is reset even when evaluation raises.
- **Board selection:** The greedy and swap search retains candidate boards, capacity states and scores for subsets it visits repeatedly. Search order, tolerances, progress comparisons and candidate enumeration remain unchanged.
- **Shop simulation:** Cumulative level odds are prepared once per simulation rather than recalculated for every shop slot. Initial owned copies are reused from the existing preparation pass. Shop draws, purchases, pool depletion and every rollout remain unchanged.
- **Evidence:** Historical evidence and model hashes reuse their existing exact encodings within the request. Live rebuilds current advice, timestamps, validity and evidence even when it reuses simulation results.

## Project-wide latency map

| Path | Finding | Consequence |
| --- | --- | --- |
| Capture | The configured poll interval is 250 ms normally and about 66.7 ms during roll-down. | A game change can wait for a capture tick before OCR or the Engine starts. |
| OCR and board recognition | Readers run on changed regions. No qualified current-game reader workload was available for this pass. | Existing model accuracy and capture behavior were preserved; this pass makes no new recognition-speed claim. |
| Fresh Engine evaluation | Profiles identify Line shop simulation and comp screening as the main costs. | Exact preparation and subset reuse help, but the large fixture still misses 100 ms. |
| Unchanged Live rereads | Equivalent stochastic inputs previously reran simulation. | Bounded exact reuse removes that work while retaining current qualification and evidence. |
| Historical planning | Live previously refolded every earlier planning snapshot. | Unchanged prefixes now reuse plans. Prefix comparisons and retained snapshots still grow with history. |
| Evidence and delivery | Evidence construction remains CPU work; the existing summary budget is 256 KiB. | Evidence must be measured alongside the Engine. It is not free, even on a cache hit. |
| Review and fitting | Review uses the shared Engine and already has a historical fold. Fitting repeatedly evaluates changed models. | Shared preparation helps these paths; a small replay fixture cannot qualify a complete real-game review or fitting run. |
| Electron and React | State arrives over WebSocket and IPC; renderer code was unchanged. | No renderer or capture-to-screen speedup is claimed without a presentation trace. |

The next numerical optimization should target the remaining simulator inner loop, using the same full seeded output as its oracle. The runtime specification permits moving that loop to a compiled extension if Python still misses the budget. Such a change needs packaging and numerical parity checks on both Windows and macOS. It was not added in this pass.

## Accuracy and verification

The public regression first demonstrated the slow reconstructed-history path. A second regression showed unchanged fresh rereads executing simulation again. Both pass with the optimization. Additional public tests compare complete decision evidence after changed history, sightings, data with the same visible ID, game changes, stale coverage, gold changes, mode changes and LRU eviction. Cache diagnostics are excluded from decision-evidence parity because they intentionally describe the different amount of executed work.

The large Engine fixture also retains exact serialized advice and Line results. The Live history fixture retains the same decision-evidence SHA-256 digest. These checks establish preservation on the tested inputs; they do not establish production gameplay accuracy.

## Check results and limits

- The broad Python run completed with **1,102 passed, 14 skipped and one failed**, plus two existing Torch ONNX-export deprecation warnings, in 1,346.93 seconds. The failed observed-roll case correctly rejected a replay because the benchmark-helper commit changed Git HEAD while the run was active. Production source was unchanged. This was not a clean full-suite gate.
- That exact case passed separately on both `aca9768` and the frozen candidate. With Git held fixed, the affected observed-roll, replay-resource, Live-delivery, Engine-runtime and combat-preview group passed **66 tests** in 31.49 seconds. No product change was needed for the input-change guard.
- All **14 skips** were confirmed to require unavailable PowerShell 7. They cover desktop launcher plans, local endpoint operator receipts and Windows launcher workflow stand-ins. They are not missing training or OCR tests.
- A separately synced public environment passed **246 Engine/Baseline/schema tests** with `tft_live` absent from distributions, import resolution and loaded modules.
- Both import contracts, schema freshness, the frozen offline lock check, scoped Ruff `F821` checks and whitespace checks passed. Renderer source, message schemas and generated UI types were unchanged; UI tests and native presentation timing were not rerun for this slice.
- Independent Standards and Spec reviews accepted the software slice. Their remaining concerns are timing-test sensitivity to host scheduling, historical-prefix growth and the distinction between sample accounting limits and a hard byte ceiling. These are not production resource qualification.

No production data, owner matches or credentials were accessed. No Windows capture, actual-game latency, recognition accuracy, renderer timing or fitted-model quality is established by these results. The fresh augment fixture still takes about 1.66 seconds, and the large fresh Engine fixtures still miss 100 ms on this machine. Those limits remain open.

## Reproduce

From `core/`, sync the checkout's normal development and Live dependencies, then run:

```sh
uv run python packages/engine/tests/benchmark_engine.py --guides 65 --rollouts 64 --repeats 7 --result-json engine-result.json
uv run python packages/engine/tests/benchmark_engine.py --guides 65 --rollouts 64 --repeats 7 --live
uv run python -m tests.benchmark_live_latency --history 12 --repeats 7
uv run python -m tests.benchmark_replay_resources --decisions 300
```

Use a clean baseline checkout and the candidate checkout with identical fixtures and dependencies. For an existing shared environment, put every intended workspace package's `src` directory on `PYTHONPATH`; verify the reported module paths before attributing results to a checkout. Compare complete outputs and evidence digests as well as times. Keep CPU benchmarks serial and separate their results from capture, device and game-running evidence.
